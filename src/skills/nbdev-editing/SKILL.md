# Editing nbdev Projects

First read and use the `persistent-python` skill - it is a must: all work here happens in that kernel using pyskills, and its rules (reprs, doc(...) inspection, raw strings) are assumed, not repeated. Style and testing process follow the `coding-patterns` skill, also assumed.

## nbdev v3

Everything here is on nbdev v3 (released Jan 2026, likely after your training cutoff). Key user-visible changes from v2: config moved from `settings.ini` to `pyproject.toml` - standard metadata in `[project]`, nbdev-specific keys in `[tool.nbdev]` (defaults now `nbs_path='nbs'`, `doc_path='_docs'`), version in `__init__.py` exposed via `dynamic = ["version"]`, and `_modidx` registered under `[project.entry-points.nbdev]`. CLI commands use hyphens, not underscores (`nbdev-export`, `nbdev-test`, `nbdev-readme`, ...), though the Python functions keep underscores (`nbdev_export`). GitHub workflows use the v3 actions (`fastai/workflows/nbdev3-ci`, `quarto-ghp3`).

Also related: it's now fastcore.nbio, not execnb.nbio. Although you normally shouldn't need nbio since pyskills has helpers for the common tasks. Only use nbio if you really need special case code.

## Source of truth

- The `.py` files are AUTOGENERATED - never edit them. Each section carries a marker like `# %% ../nbs/04_usage.ipynb #a45f753a` giving the exact source notebook and cell id: use it to jump from module code to the cell.
- `__all__`, `_modidx.py`, and module docstrings are regenerated on export - renames and additions propagate; never hand-edit.
- The module docstring comes from the notebook's opening markdown cell, so module-level prose is edited there.

## The notebooks ARE the documentation

- To understand what a module does or why, the first step is ALWAYS to read its notebook in full: `view_nb(path)`, with `incl_out=True` when behavior is the question, since the stored outputs show what the code actually does. The interleaved prose, examples, and tests are the design rationale; no README, docstring, or probe gives more.
- Read the notebook BEFORE running ephemeral checks in the kernel. Ad-hoc probes of "what happens if..." usually re-derive, slowly and less reliably, what an existing example cell already shows. If after reading you still genuinely need an experiment to answer a behavior question, that's a gap in the notebook: add the check as a proper example/test cell there, so the next reader doesn't repeat it.
- For project-level questions, read `nbs/index.ipynb`, not `README.md`: the README is generated from it, renders worse (no cell ids, flattened outputs), and can be stale if regeneration lagged. They should match; when they don't, index.ipynb is the truth. Regen with `nbdev-readme` after editing it.

## Read before you edit

- `summary_nb(path, maxlen=120)` first for anything sizable: one newline-escaped line per cell (id, type, source start), giving a cheap map of the notebook. Then `view_nb(path)` when you need the full story in order with cell ids. Never use index arithmetic or JSON spelunking.
- `nbrg(pattern, root, maxlen=120)` searches notebook cell sources and always displays one newline-escaped summary line per matched or context cell; return results bare. Export cells are visible at a glance since previews start with `#| export`.
- `find_cells(path, pattern, context=N)` shows matching cells with their neighbors; pass `summary=True, maxlen=120` for the same one-line form as `summary_nb`. `ids=`, `header_section=`, and `headers_only=` give targeted or outline views. Use it whenever you want one section of a notebook, never `view_nb` output sliced by hand. When searching, normally keep the default `context=1` rather than passing `context=0`: the adjacent markdown cell is usually the explanation of whatever you matched, so suppressing neighbors discards exactly the context a find is for. `find_cells` is for finding; to fetch cells whose ids you already know, that's `view_cells` (the one id-based `find_cells` idiom worth keeping is `ids=` plus context, meaning "this cell and its surroundings").
- `lnhashview_cell(path, id)` before any edit that might touch a cell - if there's even a chance you'll edit, use it over `view_cell`, so the `lineno|hash|` addresses are already on screen to copy literally (computing addresses from view output by string-slicing is a workaround smell). The `lnhashview_*` results display verbatim with a tuned repr (like `SearchResults`): end the cell with the bare call, and never reformat them by hand (no `'\n'.join(...)`, no slicing). `view_cell` is for pure reading only.

## Editing cells

- `doc(pyskills.ipynb)` covers the operations - don't guess signatures. Use `add_cell(..., before=|after=)` for new cells (returns the new id); `exhash_cell`/`%%exhash` for edits within a cell (the `cell_*` functions only where exhash can't express the edit -- e.g. a uniform replace across many cells is one `cell_str_replace` with an id list or 'all', not N hashed edits). Do NOT splice with `read_nb`/`write_nb` internals - if a primitive is missing, stop and ask.
- Whole-cell rewrite: `%%exhash <path> <cell_id> % c` with the new source as the payload, verbatim - `%` addresses the whole cell (no hashes needed: a full replace has no neighboring lines to mis-hit), and the payload is never parsed as Python, so triple quotes, backslashes, and mixed quote styles all pass through untouched. `%%exhash <path> % c` is the whole-file twin. For partial edits within a cell, see the `persistent-python` skill's exhash patterns (hashed addresses from `lnhashview_cell`, range-`c` for inner regions).
- Every operation returns a diff: read it, that's the immediate verification. Don't add ad-hoc parse checks; real verification is the notebook test run.
- New exported cells need `#| export` as their first line. A private helper (underscore name) can share a cell with its public consumer; nbdev keeps it out of `__all__`.
- Docstrings: never include links - write `symbol` in backticks and nbdev auto-links when published. Preserve docments (trailing `# comments` on params).

## Notebook style for changes

Two kinds of nbdev project: published libraries (fastcore, fasthtml, pyskills, ...) with rendered docs pages, and internal apps (e.g. solve-lp) with no docs site. The docs-driven conventions below matter for libraries; internal apps are looser - there, match the surrounding notebook's existing style rather than imposing these.

- Critical: NEVER mix import lines with other code in one cell, in ANY cell, tests included. The docs build executes every cell that contains an import, in a fresh namespace where your other cells haven't run, so a mixed cell either breaks the build with a NameError or silently runs at doc time. Imports go in the notebook's import cells.
- Follow the narrative: an exported cell's explanation goes in a markdown cell *after* it (docs render as the symbol, then its prose and examples). Often that one md cell does double-duty: it explains the exported code *and* introduces the first example that follows. Markdown introducing a later test/example goes before that cell, saying what it demonstrates.
- Tests and examples ARE the documentation: they render on the docs page. Write them to be read, with realistic values, minimal mocking, asserting the behavior a reader would want shown and displaying a useful output where appropriate.
- Write each example cell as if for the docs page first, then make it assert. If multiple tests/examples need some shared setup, extract a tiny helper in its own cell with a line of md saying why; a test cell that needs a paragraph of inline setup is a docs smell. A test cell >8 lines is a smell too.
- Tests use the fastcore.test helpers (`test_eq`, `test_fail`, ...) in plain code cells.
- `from fastcore.utils import *` in an early cell already provides `os`, `Path`, etc. - don't re-import those later.
- Tests are plain cells sharing the notebook's sequential state. Reuse the objects earlier cells created (`db`, `user`, ...) instead of making new ones - and don't reassign them (`u = await db.t.user[x]`, not `user = ...`): later cells depend on that state.
- Prefer extending an existing test cell over adding a near-duplicate one.
- Cells hitting live services (Stripe, running servers) are marked `#| eval: false`.
- Keep necessary-but-unreadable checks in `#| hide` cells: CI still runs them, the docs page stays clean.

A real before/after. This single cell (abridged) broke the docs build through its embedded import, and taught a reader nothing:

```python
import tempfile
with tempfile.TemporaryDirectory() as td:
    pd = Path(td)/'profile_default'
    (pd/'startup').mkdir(parents=True)
    (pd/'ipython_config.py').write_text("c.InteractiveShellApp.extensions.append('_ext_a')\n")
    (pd/'startup'/'00-start.py').write_text("startup_ran = 7\n")
    os.environ['IPYTHONDIR'] = td
    try:
        sp = CaptureShell(path=td, profile=True)
        test_eq(sp.user_ns['startup_ran'], 7)
        # ...three more asserts, then env and module cleanup...
    finally: del os.environ['IPYTHONDIR']
```

The rewrite: a four-line `_tmp_profile` contextmanager in its own cell (import moved to the imports cell), then one cell per claim, each introduced by a line of md, with the sys.path-fiddling extension check kept in a `#| hide` cell:

```python
with _tmp_profile(startup="a=7\n"): test_eq(CaptureShell(profile=True).user_ns['a'], 7)
```

## Export, test, reload

- Export via Bash with a bare `nbdev-export` run from the project directory (`cd /abs/path/proj && nbdev-export`), NOT in-kernel `nbdev_export()`. A full export is basically instant even for very large repos, so almost never scope it with `--path`/`--file_re` - partial exports just add ways to leave sibling modules stale.
- Verify edits with targeted `%nbrun` runs of the edited/affected cells (several ids run in the order given, e.g. `%nbrun <imports-id> <def-id> <test-id>`; `--above` rebuilds the state a cell depends on), red-green style: run the new test cell to see it fail, make the change, export, re-run to see it pass. Most ipynb files are fine to nbdev-test, but some are slow or require API keys, so plan to run `nbdev-test` on the changed notebook when done making changes, but check with Jeremy first before you actually do it. Once you know an ipynb or project is safe to run, go ahead without checking as needed (known safe: all of pyskills).
- Run notebook tests with `nbdev-test --path /abs/path/nbs/foo.ipynb` via Bash (absolute path resolves the right project; no cd needed), NOT in-kernel `test_nb`: the persistent kernel isn't the main thread, so anything signal-based (e.g. cell timeouts) can't work there, and a separate process can't pollute kernel/process state. To test several notebooks in one parallel run, pass a directory plus a glob: `nbdev-test --path /abs/path/nbs --file_glob "0[05]_*.ipynb"` (`--path` takes one path and does not brace-expand; `--file_glob` is the multi-notebook mechanism).
- Reload gotcha: after exporting a change to a library, reloading one module is NOT enough - modules that did `from x import *` at import time hold stale references, and `@patch` (fastcore's monkeypatch decorator, used throughout this ecosystem) mutates a class object in place, so reloading a module that defines a patched class orphans every `@patch` any *other already-imported* module applied to the old class object. Finding every such patcher to reload in the right order is forensic and fragile (grepping for the missing method is itself a workaround). <!-- claude -->Use `mcp__clikernel__restart` instead - it kills and respawns the kernel process, so `sys.modules` is genuinely reset.<!-- /claude --><!-- codex -->Restart clikernel instead: use its restart tool when available, or exit the CLI process and start a fresh one.<!-- /codex --> Reserve manual reload-in-place for a leaf module you're sure nothing else patches. If a "fix didn't take" or you see an unexpected `AttributeError` on a class you know has the method, suspect stale classes from a partial reload first.
- After `restart`, redo whatever setup the task needs before continuing: re-import `pyskills` modules and any other packages, and re-run `%nbopen` if you were using notebook magics. Session state (variables, imports, prior `pi`/`rga`-style handles) is gone.
- A notebook edit is invisible to installed code until export - say so when handing over, or export as part of the change.

## Ecosystem

- The non-standard deps are in-house nbdev projects in sibling dirs (`../fastcore`, `../fasthtml`, `../nbdev`, ...), all editable installs. Fix problems at the source project rather than working around them downstream - same workflow applies there.
- Search/read those siblings with `nbrg`/`view_nb` too - exact cell hits beat line-based context since cells are split semantically.
- `ipykernel_helper` has kernel helpers worth knowing: `info_md(obj)` for `?`-style inspection (its file:line plus the `# %% ../nbs/... #cellid` marker in the .py jumps you to the source cell), and `read_url`/`read_gh_repo` for reading docs pages, llms.txt files, and GitHub repos as markdown instead of hand-rolling httpx.

## Common gotchas

- Read the whole notebook (`view_nb`) before describing what a module does - don't infer behavior from a filename or `summary_nb` alone (`ghapi.page` sounds like GitHub Pages; it's actually pagination).
- Never hand-roll `json`/`bash`/`grep` to inspect or search notebooks or nbdev projects (e.g. finding cells with error output) - use `view_nb`/`summary_nb`/`nbrg`. If the pyskill genuinely can't answer the question, stop and propose extending it (that's how `view_nb`'s `only_errors` and the cut/copy/paste cell tools got added) rather than working around the gap.
- Don't add defensive scaffolding (`hasattr`, `try/except`, slicing) around a plain pyskill call "just in case" - call it directly and read the bare result. The tooling is designed to just work; assuming it needs a workaround is usually wrong.
- When adding new functions to a notebook, mirror the existing narrative rhythm cell-by-cell: one function, one markdown explanation, one focused test - not several defs bundled together followed by one big multi-operation test at the end.
- `#| eval: false` skips the *whole* cell, not just an assertion inside it - before marking a cell skipped, check whether later cells depend on variables it defines; cascade `eval: false` to those too or they'll `NameError`.

## Before you wrap up

Check every one of these against each cell you touched. They all fail silently: tests pass, export succeeds, and the damage only shows on the docs page or the next reader.

- **Imports stand alone**: no cell mixes imports with other code, tests included.
- **Docs-first**: test/examples cells read as documentation, not like pytests
- **Narrative rhythm**: exported cell, then md explanation and first example intro after it, then focused example; matches the surrounding notebook's cadence.
- **State flows down**: later cells reuse objects earlier cells created, and nothing reassigns a name later cells depend on.
- **Red-green ran**: each new test failed before the change and passed after, via targeted `%nbrun` (using `--above` first to set up state as needed).
- **Page read**: re-read the touched section (`view_nb` or `find_cells` with context=) as a reader would; it should read as docs, not as a test file.
